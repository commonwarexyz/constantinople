Implementation plan · Constantinople

Continuous DKG resharing over stateful consensus

Replace the epoch-zero engine with a 1,024-block epoch lifecycle in which committee state is consensus-committed, lookup addresses travel with DKG epoch artifacts, and validators can join or leave through signed transactions.

Brief

Move Commonware to cl/dkg-peer-manager; layer glue::dkg over glue::stateful; migrate discovery to lookup; add register/remove committee transactions and an epoch-indexed QMDB with carry-forward; and add a participant-selection page that respects the provider lock boundary.

01

Target data flow

The application remains the owner of transactions and QMDB commitments. The DKG layer reads only stable, epoch-addressed committee state and turns it into certified EpochInfo. Lookup consumes the exact address directory carried by that artifact.

Solid lines are consensus/data dependencies. Dashed lines are recovery or finalized-event paths. Highlighted components are new or substantially replaced.
Epoch E · heights 0–1022

Stage E+2 membership

Each SetCommitteeMember transaction clones row E+1 on first use, then idempotently registers or removes one peer in row E+2. Block order resolves multiple updates.

Epoch E · height 1023

Lock and announce

The proposer and verifier exclude committee transactions. The provider returns row E+2, or row E+1 when absent, then resolves the exact address union for the DKG payload.

Final-block system transition

Materialize fallback

After the wrapper supplies EpochInfo, the inner application writes its next_players to row E+2. Every epoch becomes explicit and state-syncable.

Epoch E+1 → E+2

Reshare, then activate

E+1 runs the ceremony with the announced next players. The orchestrator installs the resulting signer/verifier and activates the selected lookup peer set in E+2.

fn apply_member(tx, epoch, rows) {
  require(tx.target_epoch == epoch + 2);
  require(!epocher.is_last(height));
  let set = rows.get(epoch + 2)
      .unwrap_or_else(|| rows.get(epoch + 1));
  set.assign(tx.peer, tx.registered);
  require(!set.is_empty() && set.len() <= MAX);
  rows.put(epoch + 2, set.canonical());
}

05

Risks and mitigations

Permissionless committee changes are demo-only
Low
Accept updates from every valid signed account as requested, document the trust model prominently, and leave the execution policy behind a narrow authorization hook for later production hardening.
Provider sees unstable boundary state
High
Follow the upstream call order exactly: epoch_info runs before inner propose/verify at height 1023, so reject committee actions in that block and derive E+2 only from its height-1022 parent state.
Eligible address catalogs diverge
High
Generate one canonical catalog for every node, commit its digest at genesis, and reject startup if selected peers lack an address. Directory coverage must be exact.
DKG secrets are lost or returned before durable
High
Implement atomic, fsynced, permission-restricted secret writes before futures resolve; test crash/restart after each share, seed, and dealing write.
Chain schema is incompatible
High
Use a coordinated new genesis: transaction tags, block payloads, a third state commitment, and epoch semantics all change hashes.
Boundary block pruned before recovery
Medium
Keep the existing 1,024 marshal-block retention and assert the Commonware pending-ack retention inequality in config tests.
Discovery and lookup nodes cannot interoperate
Medium
Coordinate a full-cluster cutover and validate symmetric versus asymmetric/NAT addresses in generated local and remote bundles.
Browser races the lock height
Low
Poll and disable optimistically, but let proposer filtering and verifier rejection decide. Preserve typed rejection status for each submitted transaction.
06

Resolved protocol choices

Resolved: every signed account may alter the demo committee

No governance allowlist is added in this integration. The normal transaction signature and nonce still prevent spoofing and replay, while peer eligibility, epoch targeting, committee bounds, and the final-block lock remain consensus-enforced. Keep this as an explicit policy hook so a production deployment can replace it.

Decision: permissionless demo policy

Resolved: the upstream final-block call is the lock boundary

For epoch E, reshare::Application calls epoch_info before invoking the inner application’s propose or verify at height E×1024+1023. Therefore E+2 membership is exactly the parent state through height E×1024+1022: committee actions are accepted in non-final blocks and consensus-rejected in the final block. There is no configurable earlier cutoff.

Decision: lock immediately before the final block

Resolved: eligible peer addresses are immutable

Registration/removal selects from a genesis-hashed key-to-address catalog. This integration adds no address-update transaction or mutable address registry; changing an eligible peer address requires a coordinated new genesis/restart.

Decision: immutable catalog

Definition of done

✓All Commonware packages resolve to the branch commit from one source, with Rust 1.95 and a passing workspace build.
✓Blocks 1023→1024 and 2047→2048 rotate through DKG-orchestrated Simplex epochs without restarting the application.
✓Register/remove transactions deterministically produce the E+2 set; absent updates carry E+1 forward and materialize it.
✓Final blocks reject committee mutations, while transfers remain valid and the DKG payload matches the stable parent state.
✓Lookup activates the exact dealers/players/next-players union from certified addresses; missing or extra directory entries fail.
✓A node can restart or state-sync across a boundary, recover DKG state, and join as a future player before activation.
✓The explorer lists the full eligible catalog, submits multiple per-peer updates, and reports boundary, eligibility, or committee-size failures.
✓just lint, just test, just build, and explorer test/build pass on the new genesis configuration.
